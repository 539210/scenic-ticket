## 架构观察

- `AppFrame.java` 约 2206 行，承担页面构建、输入解析、DTO 格式化、权限入口和业务编排，已达到必须渐进拆分的规模。
- DAO 基本使用 PreparedStatement；动态 `IN` 仅动态生成占位符，不拼接用户值。
- 当前订单事务只包裹单表插入，没有库存锁定/扣减、支付、退款或核销。
- `BusinessService` 在 MySQL 提交后同步写 MongoDB 行为日志；日志失败会向 UI 抛错，造成“订单已落库但用户看到失败”的危险不一致。
- 管理员检查仅存在于 Swing 层，任何能获得 Service 的调用者都能执行管理操作或任意订单状态更新。
- MongoDB ID 读写仅按数值 long 匹配，无法兼容课程示例或历史字符串 ID。

## M0 结论

当前版本可编译、现有单元测试全绿，但与目标的完整售票业务仍有结构性差距。最先处理的不是界面润色，而是测试库隔离、服务层授权、订单状态机、票种/日期/库存、退款与核销。四个已知 UI 问题的相关代码近期已有改动，必须用回归测试和真实数据夹具判断“仍可复现”还是“已修但未验证”，不能凭静态阅读直接关闭。

只读数据库复现进一步确认：当前 MongoDB 的简介和评论中文已实际损坏为问号，而不是本实例中的 ID 类型不匹配；推荐 Service 当前能产生非零分数；现有审计 user/type/level 组合可工作但完整目标条件缺失。详见 `docs/KNOWN_BUG_REPRODUCTION.md`。
