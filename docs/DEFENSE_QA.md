# 数据库课程答辩问答

更新时间：2026-07-14

## 架构与选型

### 1. 为什么同时使用 MySQL 和 MongoDB？

MySQL 保存需要事务和外键的用户、票务、库存、订单、退款、核销；MongoDB 保存结构变化更频繁、写入和聚合较多的详情、评论、行为和审计。跨库关系由数值 `user_id/item_id` 和 Java Service DTO 组合，避免分布式事务伪装成强一致。

### 2. 为什么没有使用 Spring？

课程要求强调 Java Swing、JDBC、DAO、事务和数据库对象。本项目直接使用 JDBC + HikariCP，让事务边界、行锁和 SQL 调用容易展示与解释，避免引入与课程目标无关的框架复杂度。

### 3. Swing 为什么不会因查询数据库而卡死？

数据库按钮统一进入 `SwingTaskRunner` 后台执行；UI 回调回到 EDT。会话代次阻止退出后的旧任务回写，同名最新请求代次阻止旧查询覆盖新查询，glass pane 在任务期间阻止重复提交。

## MySQL 与事务

### 4. 如何防止库存超卖？

创建待支付订单时，在同一 JDBC 事务和连接内锁定 `ticket_inventory` 行，校验可售数量并把 available 转为 reserved。支付把 reserved 转为 sold；取消/过期释放 reserved；退款把 sold 恢复为 available。真实并发测试让 20 个线程争抢 10 张票，只有 10 个成功且库存桶守恒。

### 5. 为什么订单先待支付而不是直接已支付？

创建和支付是两个用户动作。创建只预留库存并写 15 分钟过期时间，状态为 0；用户主动确认后才在事务中变为 1。这样能展示真实订单状态机，也避免把下单等同支付。

### 6. 如何处理订单过期？

查询订单时触发受限批量扫描，逐单锁定已到期待支付订单，释放预留库存并标记取消。历史订单可能没有对应预留桶，此时只兼容取消，不虚增库存。

### 7. 退款为什么安全？

事务内锁订单，校验已支付、游玩日期未到、无核销、无既有退款，然后恢复 sold 库存、插入唯一退款记录并更新订单。任何一步失败都回滚；已完成、已核销、到期或重复退款均拒绝。

### 8. 核销如何支持多人分批入园？

`admissions` 每次保存数量、管理员、时间和备注。事务内锁订单并统计已核销数量，累计达到订单数量时订单转为已完成；任何核销记录都会禁止退款。

### 9. 乐观版本号和行锁分别做什么？

核心库存与订单转换以 `SELECT ... FOR UPDATE` 行锁保证当前事务串行；`status_version` 保存状态版本，为条件更新和未来并发扩展提供额外检测，不替代事务锁。

### 10. 项目用了哪些高级数据库对象？

两个视图 `v_user_profile`、`v_item_order_summary`；两个存储过程 `sp_monthly_order_report`、`sp_update_inactive_items`；两个触发器 `trg_orders_before_insert`、`trg_items_before_update`。M10 空库和真实测试验证对象存在并实际调用。

## MongoDB 与跨库

### 11. 如何保证同一用户对同一景点只有一条评论？

MongoDB 使用 `user_id + item_id` 唯一索引，服务使用 upsert；再次提交保留 `created_at`、更新正文/评分与 `updated_at`。并发唯一冲突会重试为更新。

### 12. 历史字符串 ID 怎么兼容？

DAO 查询数值 Long 和等值数字字符串；再次保存时按原 `_id` 原位更新并把引用规范为数值。迁移脚本只转换可安全识别的数字字符串，不删除重复评论。

### 13. MySQL 成功但 MongoDB 日志失败怎么办？

订单、用户管理等核心事实以 MySQL 提交为准。Mongo 审计是提交后的安全写入；失败时返回“业务成功但审计失败”的明确警告并写本地日志，不回滚已提交 MySQL，也不诱导用户重复操作。

### 14. 跨库查询是否有分布式事务？

没有伪造分布式强一致。景点主数据先从 MySQL 查询，再按 ID 查询 Mongo 详情/评论并组合 DTO。写入失败采用明确的补偿或降级策略，例如新景点详情保存失败会尝试下架 MySQL 景点。

### 15. 使用了哪些 MongoDB 聚合？

用户行为汇总、用户综合报告、热门景点、行为类型、每日趋势、评分摘要/分布、系统审计汇总/趋势和用户操作汇总，超过课程要求的三个。

## 权限、安全与测试

### 16. 为什么隐藏管理员按钮还不够？

UI 可以被绕过。所有管理写入、系统审计和私有数据查询都接收 actor ID，并由 `AuthorizationService` 从 MySQL 回查账号启用状态和角色；普通用户直接调用服务也会失败。

### 17. 如何保护最后一个管理员？

管理员用户变更在事务和行锁中执行，禁止操作自己，并在禁用/降级前统计有效管理员；如果目标是最后一个有效管理员则拒绝提交。

### 18. 密码和配置如何保护？

密码使用 BCrypt，只保存哈希；SQL 使用 `PreparedStatement/CallableStatement`。真实凭据只存在被 `.gitignore` 排除的 `db.properties`，提交前扫描 Token、私钥和连接串凭据。

### 19. 如何证明迁移不会破坏旧数据？

`verify-mysql-upgrade.ps1` 只允许重建 `scenic_ticket_test`，先安装 Day08 历史夹具，再逐个执行 Day09 正向迁移，最后断言历史用户、档案、订单和课程字段仍在。M10 实测通过。

### 20. 测试覆盖到什么程度？

M11 最终默认 Java 21 套件 158 项；启用隔离 MySQL/MongoDB 后 172 项，0 failures、0 errors。覆盖单元、页面组件、文档一致性、权限、事务回滚、库存并发、Mongo 索引/UTF-8/聚合、数据库对象、跨库和双角色端到端流程。

### 21. 当前还有什么限制？

跨库读取仍是同步顺序组合，不是高并发分布式架构；历史已损坏成问号的中文不可逆，只能提示管理员按原资料重填；真实 Swing 视觉/连点/断库清单必须由能看到桌面的执行者最终勾选。Mongo JS 脚本已由 Java Driver 和官方 `mongosh` 双重验证。
